## 0. 一句话结论

M3 不是「再加四个系统」,而是**把 M2 留下的四个恒 1.0 的乘数槽真正填满,同时补上 M2 因为数据缺口被迫跳过的一整层内容**。

盘点结论:

- 七乘数槽里 **恒 1.0 的是四个不是三个**——`npc` / `tool` / `event` 之外,**`power` 电力在 M2 从头到尾没被认领**(v3.2 §19 的 M2-C1~C6 清单里没有电力这一节,`power_per_min` seed 了 57 行至今零读取)。EVT_BLACKOUT 直接依赖它。
- **§13 的 2.75× 硬帽在 M3 会被打爆**:满配 `tech 1.20 × npc 1.90 × tool 1.18 = 2.69`,留给事件的余量只剩 **2.2%**。四个系统全部上线后正向事件对强城市 **100% 无效**,只有负面事件生效。这是必须先拍板的平衡问题,不是实现细节(测算见第 11 节)。
- **§8.1 的市场公式缺「滑点」**:§13 明文要求「手续费、成交量上限、滑点和移动平均必须同时存在」,但 §8.1 只给了前两项和移动平均。且 24 种可交易资源的 `volatility` 全部 ≥ 0.04,其中 14 种 ≥ 0.07,而买卖价差只有 6%(2×fee)——**纯噪声套利在数学上成立**。
- **M2 遗留 14 项**,其中 6 项是「时代升级维度被跳过」造成的玩法空洞(资源节点、稳定税收、区域/远程贸易、电网稳定…),这些恰好都要靠 M3 的系统才能补上——所以 M2 遗留不是「附带清一下」,它和 D 轨道是同一批工作。

### 5.2 价格窗口 Scheduler

- `window_index = floor((now − EPOCH) / 窗口秒)`,**绝不依赖常驻 worker**;cPanel cron 最细 1 分钟、会漏跑 / 延迟 / 并发 → 每次执行补算「上次已生成的 window_index+1 … 当前」,配 `withoutOverlapping`,靠 `UNIQUE(resource_id, window_index)` 兜底重复。
- §2.2 建议 ≈30 秒窗口,与共享主机 cron 的 1 分钟粒度冲突 → **需拍板**(见 9.C2)。
- `eventMultiplier` 由 EVT_OIL_SHOCK / EVT_SPECULATION 写入,默认 1.0(D4 依赖点)。

### 5.3 API

| 端点 | 说明 |

### 6.2 触发引擎

- 60 秒**资格窗口**批量判定,不做全表扫描:城市在 Time Delta 结算时按经过的窗口数补算(§9.1)。
- 基础概率 8% / 窗口;权重 = `baseWeight × 条件修正 × 城市状态修正 × 难度修正`(三个修正系数是 §16.5 的缺口,见 9.D2)。
- 并发上限:同时最多 3 个,其中灾害 / 国防类最多 1 个;同 `event_id` 受冷却限制。
- **离线补算是最容易做错的一处**:12h = 720 窗 × 8% ≈ **期望触发 57.6 次**。不设上限玩家上线会被几十个事件淹没;但用 `1-(1-0.08)^n` 一次性判定又会丢失冷却与并发上限语义。裁决见 9.D3。
- **随机数必须服务器权威**(§30 / §66):用 PHP `random_int()`,禁止任何客户端参与;掷出的结果落 `rolled_json`,resolve 时不再重掷(否则玩家可以刷选项)。

### 6.3 API

| 端点 | 说明 |
|------|------|
| `GET /api/city/events` | 当前 active 实例 + 剩余时间 + 三个选项文案 |
| `POST /api/city/events/{instance}/resolve` | 入参 `option`(a/b/c)。§70 五道校验:属于该玩家 / status=ACTIVE / 未过期 / choice 合法 / 未领取 |

安全链:全链 + Idempotency + `expected_revision` + Audit `EVENT.TRIGGER` / `EVENT.RESOLVE` / `EVENT.REWARD`。
**同一 instance 不允许二次结算**——靠 `status` 的条件更新(`UPDATE … WHERE status='active'` 的影响行数为 0 即已被领)而不是先查后写,避免并发双领。
新错误码:`EVENT_EXPIRED`(§32 已列)、`EVENT_ALREADY_RESOLVED`、`EVENT_OPTION_INVALID`。

### 6.4 结算内核接线点

- `multipliers['event']`:从 `city_active_modifiers` 取产量类修正。
- **事件对幸福 / 治安的冲击**:走 D0.2 的 flat 通道。分两类——
  - **瞬时型**(EVT_FESTIVAL 幸福+4、EVT_STRIKE 治安-6):直接改当前值;
  - **持续型**(duration_minutes > 0):改**目标值**,由 §10.2 的快落慢升自然收敛(否则会和 M2 已实现的收敛模型打架)。
  这条口径需明确写进注释与测试,是 M3 最容易埋 bug 的地方之一。
- 负面事件的资源直接损失(EVT_GRANARY_PEST 粮食 -8%~15%)在分段结算的**段起**一次性扣,不摊到整段。

### 6.5 前端 / 后台 / 测试

前端 `event-dialog.js` + `notification.js` 独立化(M2 遗留:现在 toast 是单例 div + 单 timer,第二条会顶掉第一条)。
后台:事件定义编辑、**手动给指定城市触发 / 取消事件**(必填 reason + 审计,这是运营与复现 bug 的关键能力)、`event_enabled` 全局开关。
测试(§15 两条 + 补充):冷却期内不重复抽中;同一 instance 重复 resolve 只结算一次;过期事件被拒;越权 resolve 他人事件;离线 12h 事件数量不超上限;持续型 modifier 跨段正确生效与到期失效。

## 10. 依赖与顺序 + 2-agent 并行波次切分

### 10.1 硬依赖图

```text
D0 modifier 总线 ─┬─→ D1 NPC ──┬─→ D5.4 军事NPC
                  ├─→ D2 工具 ─┘
                  ├─→ D4 事件 ──→ D5.2 EVT_RAID
                  └─→ M.1 电力 ──→ EVT_BLACKOUT(D4)

G Scheduler(window_index) ─┬─→ D3 市场价格窗口
                            └─→ D4 事件资格窗口(共用 EPOCH)

M.2 两份映射草案(等审批) ──→ D3 市场上架 5 种无源资源(§16.1 的③)
                          └─→ 时代 IX/X 建筑解锁

D3 市场 ──→ M.7 的「区域贸易 / 远程贸易」时代维度
D5.1 威胁等级 ──→ D4 的 EVT_RAID / EVT_BORDER_TENSION 条件判定
M.1 电力 ──→ M.7 的「电网稳定」时代维度
```

**关键顺序结论**

1. **D0 必须第一波**,且必须由单一 agent 完成——它是全 M3 唯一一次 `SimulationService` 结构性改动,后续所有系统只实现 Provider,不再碰内核。
2. **市场依赖 M.2 草案审批**:B1 裁决的③(水泥 / 药品 / 黏土 / 砂石 / 电子元件上市)是 D3 的价值前提。审批不下来,D3 可以先做机制,但 5 种资源不能上架。
3. **事件依赖治安 / 威胁等级**:EVT_CRIME(治安<65)、EVT_RAID(威胁等级≥中)的条件判定必须先有 D5.1,否则 30 条里有 4 条永远触发不了。
4. **NPC 不依赖工具**(两者是独立乘区,§7 明文「工具加成与 NPC 加成属于不同乘区」),可以并行——但**两者都依赖 D0**。
5. Scheduler(`window_index` 补算 + `withoutOverlapping`)是市场与事件的**共同硬前置**,放第一波与 D0 并行。

## 11. 风险

### 11.1 §13 硬帽的实际余量测算(🔴 最高优先,建议开工前拍板)

七乘区里 `worker` / `power` / `logistics` 只会 ≤1.0(打折方向),真正往上顶的是 `tech` / `npc` / `tool` / `event` 四项:

| 乘区 | 上限来源 | 满配值 |
|------|---------|:---:|
| `tech` | §5:同分支每解锁一条 +2%,每分支 10 条(10 时代 × 5 分支 = 50) | **1.20** |
| `npc` | §6.4:多 NPC 叠加后总封顶 | **1.90** |
| `tool` | §7:同类取最高;产量类最高 `industry_output_pct 18` / `knowledge_output_pct 35` | **1.18 ~ 1.35** |
| `event` | §9.2:最强正向单厂效果 EVT_CRAFT_DISCOVERY 选项 B「单厂+30%」 | **1.30** |

| 组合 | 乘积 | §13 普通帽 2.75 | 结论 |
|------|:---:|:---:|------|
| tech × npc | 2.280 | 余量 **1.206×** | 还有空间 |
| tech × npc × tool(1.18) | **2.690** | 余量 **1.022×** | **留给事件只剩 2.2%** |
| tech × npc × tool(1.18) × event(1.30) | 3.497 | **溢出 27%** | 正向事件完全被吃掉 |
| tech × npc × tool(1.35) × event(1.30) | 4.001 | 终局帽 3.25 仍 **溢出 23%** | 终局建筑同样打爆 |

**后果**:满配城市的正向事件、甚至工具,收益为 **0**——但负面事件(乘数 <1)照常生效。玩法上变成「越强越只吃惩罚」,且玩家花资源做的工具看不到任何数字变化,是最容易被投诉「功能没用」的一类 bug。

**四个可选方向(需拍板)**:①把 NPC 总帽 1.90 下调到 1.50(乘积降到 2.12,余量 1.30);②工具与事件改为对 `base` 做加法而不占乘区;③把 §13 普通帽提到 3.5 / 终局 4.0;④保持现状,但正向事件效果一律改成「直接发放资源」而非乘区加成。**起草人倾向 ① + ④ 组合**。

### 11.2 市场经济安全(§69 九面 + §13 四件套)

- **纯噪声套利在数学上成立**:§8.1 的 `nextPrice = clamp(currentPrice×0.80 + targetPrice×(0.20+noise), …)` 中,当 `current ≈ target` 时 `next ≈ P×(1+noise)`,即每窗最大 ±`volatility` 的随机漂移。而买卖价差只有 `2×fee_rate = 6%`。26 种资源里 **24 种可交易资源的 volatility 全部 ≥0.04,其中 14 种 ≥0.07**(金属 / 能源 / 电子 / 终局)。一次「低买高卖」往返的期望毛利 ≈ `2×volatility = 14%~24%` **远大于 6% 的价差** → 只要玩家肯等窗口,就是稳定印钞机。
- **§13 要求的四件套里「滑点」在 §8.1 公式中根本不存在**。必须按 9.C4 补上,并且成交量上限(流动性 10%)要真的落到 `city_market_quota` 表上而不是只写在文档里。
- §69 九面逐项落地检查(服务器算价 / 服务器算费 / 校验 quantity / 校验余额 / 校验库存 / 事务 / 幂等 / 限流 / 审计),**九项缺一即可刷钱**。
- 建议 M3 上线时 `market_enabled` 默认**关**,内部灰度跑够经济回归再开。

### 11.3 事件随机数服务器权威

- 所有掷点用 PHP `random_int()`(CSPRNG),**禁止 `mt_rand`**,更禁止任何客户端参与(§30 / §66)。
- **掷出结果必须落库**(`city_event_instances.rolled_json`):EVT_GRANARY_PEST 的「损失 8%~15%」如果在 resolve 时才掷,玩家可以反复失败重试刷低损失;EVT_SPECULATION 的「50% 概率 1.7×」同理。
- 离线补算的随机数不能依赖 `now()` 作种子(玩家可通过控制上线时间刷),用 `window_index` + city_id + 服务端 secret 派生。
- resolve 的幂等必须靠**条件更新的影响行数**判定,不能「先 SELECT status 再 UPDATE」(并发双领)。

### 11.4 其他

| 风险 | 说明 |
|------|------|
| **MySQL 5.7 上线才炸** | 市场 10 窗移动平均、每城最新 N 条事件、NPC 跨级结算全是窗口函数场景。本地 MariaDB 10.4 能跑 `OVER()`,线上 5.7 直接语法错误。`release:check` 加静态 grep |
| **ALTER 超时** | M3 给 `cities`(threat_level / tax_stable_since / power 相关)、`city_building_instances`(npc_slots / item 相关)各加多列,5.7 无 INSTANT → 同表新列合并进一个迁移;新表有跨表外键,`down()` 不能是裸 `dropIfExists` 的默认顺序 |
| **Hash Chain 与并发** | 链要求顺序,而 M2 有「不变量失败在事务外补写审计」的路径。按 F5 的「每城一条链」可大幅降低串行面,但跨城管理员操作仍需单独处理 |
| **离线雪崩** | NPC 自然增长、事件触发、市场窗口补算三者都挂在 Time Delta 上,12h 离线会同时炸三处。三者都必须有独立上限,且**分段数上限 24 段的约束不能被打破**(共享主机会超时) |
| **前端面板爆炸** | M2 的 `build.js` 已经一个文件干六件事,M3 再加四个面板会失控。W5-B 必须先做模块层 / 事件总线 / bottom sheet,再挂面板 |
| **草案审批久拖** | M.2 不批 → 时代 IX/X 建筑锁死 + 市场少 5 种资源 + `BLOCKED_BY_RESOURCE_SOURCE_MAPPING` 摘不掉。这是**唯一一个纯等待、无法靠开发绕过**的阻塞 |
